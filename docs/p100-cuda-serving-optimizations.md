# P100 CUDA and serving optimisations

This document is the reproduction guide for the P100 work in the following
commits:

* `6283b67fb` — serving lifecycle, canonical KV suffix transport, bounded
  plan reuse, publication overlap, restricted tiny-MMVQ dispatch, and the
  P100 MoE `MUL_MAT_ID` MMQ exception (patch 06).
* `248bd6b57` — Pascal CUDA decode kernels and guarded GDN/CONCAT/TOP_K
  fusions, built on `6283b67fb`.

The original source and qualification references are `45fccdd5665d6c6c2f0fb669c1f630af84d0630e`
and `36bad6bb3ad4c9b31edc4dae9fb6c3716b95704b`. The code is written for
Tesla P100 (compute capability `sm_60`) and Qwen3.6-35B-A3B Q8_0. The
optimisations are opt-in or architecture/layout guarded; unsupported shapes
fall back to the existing kernels.

## Reproduction assumptions

The measured setup has four Tesla P100s, CUDA 12.8, a CUDA-compatible driver,
and GNU C++ 14. CUDA 13 does not provide the required Pascal offline
compilation support. The model used by the checked-in harness is:

```
/home/arian/models/qwen3.6-35b-a3b/Qwen3.6-35B-A3B-Q8_0.gguf
```

The harness also expects the placement evidence under
`docs/p100-pairwave-project/evidence/runtime/`. For another machine, either
provide those files at equivalent paths or update `MODEL` and `docs` near the
top of `bench/coding-serve/run.py`. Every run writes the complete command,
environment, source commit, and binary hashes to
`results/coding-serve/<tag>.meta.json`; that file is the authoritative record
for a reproduction.

Do not run two four-GPU jobs concurrently. `run.py` takes
`/tmp/affinitywave-4gpu.lock`, checks `nvidia-smi`, limits CPU workers to
`0-11`, and watches `/home/arian/.xsession-errors` and free disk space. These
guards are required on the shared P100 host, not performance features.

## Build

From the repository root, configure a clean build. Setting the architecture
explicitly is useful on a host where CMake cannot see a GPU during configure:

```bash
cmake -S . -B build-coding-serve -G "Unix Makefiles" \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.8/bin/nvcc \
  -DCMAKE_CUDA_HOST_COMPILER=/usr/bin/g++-14 \
  -DCMAKE_CXX_COMPILER=/usr/bin/g++-14 \
  -DCMAKE_CUDA_ARCHITECTURES=60 \
  -DLLAMA_BUILD_SERVER=ON \
  -DLLAMA_BUILD_TESTS=ON

cmake --build build-coding-serve \
  --target llama-server llama-bench llama-perplexity test-backend-ops \
  --parallel 8
```

The canonical project wrapper performs this configuration and additionally
compiles the boundary validator used by the serving gates:

```bash
bash bench/coding-serve/build.sh
```

It produces `build-coding-serve/bin/test-aw-serving` alongside the normal
llama.cpp binaries.

`-DCMAKE_CUDA_ARCHITECTURES=60` is the minimum P100 build. A multi-GPU
deployment containing newer cards may add their architectures, but `60` must
remain compiled. Do not use the system GCC 15 as nvcc's host compiler with
CUDA 12.8.

## Fixed-shape qualification

The protected long-prefill path is measured separately from HTTP serving. Use
the harness so that all placement, NCCL, graph, Q8 layout, and CohortRail
settings are recorded:

```bash
python3 bench/coding-serve/run.py \
  --build build-coding-serve \
  --tag qualified-8128-reproduction \
  --variant qualified --mode bench \
  --tokens 8128 --repeats 4
```

The command runs `llama-bench` with `-ngl 99 -sm tensor -fa 1 -b 8128 -ub
8128 -mmp 0 -p 8128 -n 0 -r 4`. The patch-06-only qualification recorded
`2896.223626 +/- 5.552398 tok/s` over four samples. That is a reference
measurement, not a promise for every driver or clock state. The later decode
kernel commit has not been assigned a new long-prefill rate claim.

For a direct one-off command, use the executable and model recorded in the
`.meta.json` file; do not omit the four-GPU environment generated by
`run.py`.

## Serving

The normal launcher enables the validated serving profile, prewarms common
prompt shapes, and leaves llama-server verbose:

```bash
bash bench/coding-serve/serve.sh
```

For a remote machine on the LAN, bind explicitly and optionally enable the
embedded Web UI:

```bash
bash bench/coding-serve/serve.sh --host 0.0.0.0 --port 18097 --webui
```

The default endpoint is `http://127.0.0.1:18097`; with a wildcard bind use
the host machine's address, for example `http://192.168.1.37:18097`. A
successful health check is `/health`, and the Web UI is `/` when `--webui` is
present. `run.py` derives probe URLs from `--host`, including IPv6 literals.

The launcher profile is equivalent to these serving-specific settings:

```text
GGML_CUDA_AW_SERVE=1                 # selected by --variant serve
GGML_CUDA_AW_PARTIAL=serve-auto
GGML_CUDA_AW_SERVE_KV_PREFIX=1
GGML_CUDA_AW_SERVE_KV_SUFFIX=1
GGML_CUDA_AW_SERVE_PLAN_CACHE=1
GGML_CUDA_AW_SERVE_PLAN_CACHE_SIZE=4
GGML_CUDA_AW_SERVE_PUBLISH_OVERLAP=1
GGML_CUDA_AW_PRECAPTURE=0
GGML_CUDA_AW_SERVE_RESERVE_FULL=1
GGML_CUDA_AW_SERVE_TINY_MMVQ=1
```

The five fresh shapes `64,128,256,512,1024` are prewarmed without populating
the user's prompt cache. To run a finite smoke instead of a persistent
server:

```bash
python3 bench/coding-serve/run.py \
  --build build-coding-serve --tag serve-smoke-reproduction \
  --variant serve --mode server --tokens 2048 --ctx 4096 \
  --suite smoke --prewarm 64,128,256,512,1024 --timeout 900
```

The unmodified `run.py` environment also enables P2P, pre-Ampere graph
support, split graph buffers, Q8_1 de-duplication, FP32 cuBLAS compute,
expert sorting/EP/reuse, pinned and grouped MoE paths, the device MoE plan,
NCCL ring transport, and the CohortRail placement map. Do not reconstruct
these flags from memory: use `run.py`; its metadata file records the exact
expanded environment.

## Optimisation inventory

### P100 MoE MMQ exception (patch 06)

`ggml/src/ggml-cuda/mmq.cu` keeps dense `MUL_MAT` on cuBLAS for SM60, because
software DP4A emulation loses to the dense cuBLAS path. It permits MMQ only
for expert `MUL_MAT_ID` calls (`n_experts != 0`) on Pascal or newer. This is
useful because the non-MMQ MoE fallback performs host sorting, synchronises
the stream, and launches many small expert matmuls. The current production
EP/device-plan route can bypass this fallback; the exception remains
available for non-EP or plan-disabled MoE execution.

### Pascal integer dot-product fallback

`ggml/src/ggml-cuda/common.cuh` implements `ggml_cuda_dp4a()` with four
`vmad.s32.s32.s32` instructions when `__CUDA_ARCH__ >= 600` and native
`__dp4a` is unavailable. Older architectures retain the scalar four-byte
fallback. This is an instruction-selection change only; the accumulator and
byte operands are unchanged.

### MMVF and MMVQ decode geometry

* `mmvf.cu` permits the pre-Turing F32 MMVF path through batch width 8 (the
  previous limit was 3), subject to the existing shape checks.
* `mmvq.cu` uses four rows per block for the selected MoE MMVQ launch. The
  existing SM60 dispatch table still chooses warps and row geometry by
  quantisation, batch width, and architecture; it is not a universal
  four-row override.

### GDN and row-CONCAT fusion

`gated_delta_net.cu`, `concat.cu`, and `ggml-cuda.cu` add guarded graph
fusions:

1. A F32 beta sigmoid immediately feeding GDN can be evaluated in the GDN
   kernel, avoiding a separate activation pass.
2. A small `GET_ROWS` state gather can be deferred. The GDN kernel reads the
   selected state rows directly and can write the gathered state destination
   while it already owns the state in registers.
3. A compatible small-row F32 CONCAT (2–8 columns) uses one row kernel; the
   four-float aligned case uses a 16-byte vector transaction. A compatible
   CONCAT/GET_ROWS pair can use the deferred gather metadata.

The graph code only defers a gather when there are no concurrent stream
events, the views are contiguous and zero-offset, and no intervening node
reads or overwrites the state. Scratch row indices are device-resident and
freed with the CUDA context. Any unsupported layout or graph shape uses the
original operation.

### Pascal partial TOP_K

`top-k.cu` adds a two-stage partial selector for non-CUB builds when
`ncols >= 4096`, `1 <= k <= 16`, and dimensions fit in 32-bit indexing. It
keeps an ordered `(float,index)` key, selects per-stripe candidates, and
merges them before writing the final indices. The packed key preserves the
existing descending-value and deterministic index tie order. Smaller or
unsupported inputs retain the existing bitonic/argsort path.

### Serving lifecycle and transport

The serving changes in `src/llama-context.cpp` and
`ggml/src/ggml-backend-meta.cpp` are independent of the CUDA decode fusions:

* Full reservation keeps the common activation shapes stable.
* `serve-auto` uses the established BF16 partial path for selected short
  shapes and FP32 where required; it is not a blanket low-precision switch.
* The restricted tiny-MMVQ route applies only to the existing <=4-token
  dispatch.
* Prefix views preserve the validated padded readable KV extent. They do not
  crop to the intuitive actual-token extent.
* Suffix transport tracks a serving-state epoch and copies only newly
  appended contiguous K/V rows after a known-valid canonical prefix. Resets,
  rollback, sequence replacement, recurrent state, unsupported strides, and
  storage-generation changes invalidate the marker and take the conservative
  full-copy path.
* The bounded plan cache stores graph metadata and bindings, not duplicate
  activation arenas. It is enabled only with full reservation and is cleared
  when scheduler or memory-module updates can replace storage.
* Publication overlap removes only the redundant owner-side barrier. Each
  destination lane still synchronizes before its prior state can be
  overwritten, and the final owner-to-lane copies remain ordered.

### Source map and lifecycle rules

The implementation is deliberately spread across the graph builder, the meta
backend, and the CUDA kernels. This map makes it possible to audit or port the
work without relying on the commit message alone:

| File | Reproduction-relevant responsibility |
| --- | --- |
| `src/llama-context.cpp`, `src/llama-context.h`, `src/llama-graph.h` | Bounded serving plan cache; graph-result retention and selection; cache clearing when scheduler reservation, memory updates, sequence mutation, reset, rollback, or state load can change storage or token identity. |
| `ggml/include/ggml-backend.h`, `ggml/src/ggml-backend-meta.cpp` | Serving-state epoch; canonical KV prefix shaping; append-only K/V suffix copies; conservative invalidation; recurrent-state full copies; owner-side publication barrier elision. |
| `ggml/src/ggml-cuda/mmq.cu` | SM60-only exception that enables MMQ for expert `MUL_MAT_ID` while retaining cuBLAS for dense `MUL_MAT`. |
| `ggml/src/ggml-cuda/common.cuh`, `mmvf.cu`, `mmvq.cu` | Pascal integer dot-product fallback and the guarded MMVF/MMVQ decode launch geometry. |
| `ggml/src/ggml-cuda/gated_delta_net.cu`, `gated_delta_net.cuh` | Fused beta sigmoid, deferred state gather, state writeback, and recurrent-cache copy fusion. |
| `ggml/src/ggml-cuda/concat.cu`, `concat.cuh` | Small-row F32 CONCAT kernel and the compatible deferred-gather destination path. |
| `ggml/src/ggml-cuda/ggml-cuda.cu` | Graph traversal/deferral guards, scratch-row lifetime, fusion dispatch, and device capability checks. |
| `ggml/src/ggml-cuda/top-k.cu` | Non-CUB two-stage partial TOP_K selector and deterministic tie handling. |
| `bench/coding-serve/run.py`, `serve.sh`, `server_probe.py` | Four-GPU lock/watchdogs, complete environment construction, verbose LAN serving, host-aware probes, prewarm suites, and per-run provenance metadata. |

State invalidation is part of correctness, not just cache hygiene. A full
epoch invalidation is issued for scheduler/memory replacement, reset, sequence
replacement, state import, and unsupported rollback. A sequence removal may
retain a long known-valid prefix (position at least 4096, or only the final
four padded tokens being trimmed); ambiguous short-prefix replacement falls
back to a full invalidation because the backend cannot inspect request-token
identity. Recurrent tensors never use the append-only suffix shortcut.

## Kill switches and safe A/B testing

Every new CUDA decode fusion can be disabled without rebuilding:

```text
GGML_CUDA_DISABLE_CONCAT_ROWS=1
GGML_CUDA_DISABLE_FUSE_CONCAT_GATHER=1
GGML_CUDA_DISABLE_FUSE_GDN_GATHER=1
GGML_CUDA_DISABLE_FUSE_GDN_BETA=1
GGML_CUDA_DISABLE_TOP_K_PARTIAL=1
```

For a serving A/B, pass settings through the runner (only explicit
`GGML_CUDA_AW_*` and `GGML_META_*` names are accepted):

```bash
python3 bench/coding-serve/run.py ... --env GGML_CUDA_AW_SERVE_KV_SUFFIX=0
```

The CUDA fusion switches above are deliberately not accepted by the generic
runner's `--env` allow-list; set them in a controlled shell environment or
extend the allow-list for a local experiment. Keep one four-GPU job active and
record the resulting environment in the run metadata.

## Validation protocol

Run the non-GPU checks first:

```bash
python3 -m unittest -q bench/coding-serve/test_harness.py
bash -n bench/coding-serve/serve.sh
git diff --check
```

For CUDA operation correctness, build `test-backend-ops` and run the TOP_K
suite on one P100:

```bash
CUDA_VISIBLE_DEVICES=0 build-coding-serve/bin/test-backend-ops \
  test -b CUDA0 -o TOP_K
```

The parallel-agent campaign reported 525/525 TOP_K cases, including
151936/202048/262144/524288-column vocabularies, multiple rows, ties, and
`k` through 16. Re-run this suite on the combined commit before publishing a
new qualification number; the report is evidence from the source campaign,
not a substitute for local validation.

For serving correctness, use the boundary validator and quality mode:

```bash
python3 bench/coding-serve/run.py \
  --build build-coding-serve --tag serving-boundaries \
  --variant serve --mode validate --tokens 512 --ctx 16384

python3 bench/coding-serve/run.py \
  --build build-coding-serve --tag serving-long-quality \
  --variant serve --mode quality --tokens 8128 --ctx 16384
```

Acceptance requirements are byte-identical logits where the change is
transport/dispatch-only, or paired PPL within `+/-0.003` with KLD and
same-top-token checks when arithmetic or scheduling changes. Include fresh
odd sizes, four-token tails, cached prefixes, reset/rollback, alternating
shapes, and a decode-regression check. HTTP token rates must be reported
separately from the fixed-shape `llama-bench` rate because graph construction,
state publication, and first-token output work are included in HTTP TTFT.

## Known limitations

The plan cache is metadata-only rather than a full multi-arena scheduler
cache. Publication overlap is not full per-layer early publication. The
suffix tracker is intentionally conservative for recurrent state and unknown
storage generations. The partial TOP_K path is disabled when the newer CUB
TopK implementation is available. The MMQ exception is not expected to
improve the current EP/device-plan serving path when that path bypasses
`MUL_MAT_ID` fallback dispatch.

The documented serving matrix before the decode-kernel merge was approximately
`101.57, 193.03, 349.59, 596.26, 924.90, 1399.12, 2000.41, 2348.06`
tok/s for fresh 64 through 8128-token prompts. Those are historical serving
measurements, not a new rate claim for `248bd6b57`. Always qualify the exact
binary, driver, clocks, model hash, and environment being deployed.
